The former driver-account V2 schema is consolidated here; existing databases need the documented backup and schema-history reconciliation process.

## Known gaps and manual review

- Site operators have separate records in the `administrators` table but use the shared `/login` page with passengers. Successful sign-in routes operators to `/admin` and passengers to `/bookings`. If the configured database has no administrator, the first account can be created through the localhost-only `/admin/setup` form; the password is BCrypt-hashed, and no credentials are logged. Operators can review customer accounts, bookings, payments, refund requests, and manage the fleet. Promotion administration is not implemented, promotion records are not seeded/imported, and refunds must be executed through a real provider workflow; the panel does not automatically approve or issue them.
- Stripe Checkout requires both `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; neither a real Stripe account nor external payment was configured or tested. Card numbers and CVV are never collected or stored. Cash remains pending until a trusted driver integration confirms collection.
- Booking map tiles, address search, and driving route estimates use the Geoapify API with a server-side key and MapLibre frontend. The Geoapify key supplied in chat was not embedded and should be rotated because it was exposed. Geoapify account access and live provider requests were not verified here.
- Driver application now collects identity, address, licence expiry, vehicle details, and private profile/licence/vehicle images. Admins can search/filter, view details/documents, approve or reject with a reason; approval creates a BCrypt-hashed temporary password in the shared driver account, queues credential/rejection email after transaction commit, tracks credential delivery status, and forces a password change before the protected dashboard. Driver password reset is also implemented with single-use hashed tokens. SMTP delivery and real MySQL are not verified; no credential email is delivered unless SMTP is configured. Do not use the test inbox to send real credentials.
- Driver availability can be toggled only after account approval, credential change, and unexpired driving licence; it is not yet gated on insurance or active trips. A token-protected integration endpoint accepts GPS updates for approved online drivers; the booking map displays fresh nearby locations by vehicle category. GPS locations are short-lived in application memory and require a trusted driver app/backend feed; no real driver tracker was available for end-to-end testing. Automatic matching/assignment from the managed fleet, driver ride requests and accept/reject, driver trip operations, live browser GPS, earnings and payouts are not implemented; booking dispatch still relies on the separate external driver integration.
- Review, rating, complaint, reporting, and the sixth member's assignment remain unimplemented.
- The new application starts with H2 for local development; MySQL dependencies/configuration and Flyway DDL are present, but no real MySQL server was configured or tested.
- Passenger registration is migrated, but profile editing, password change/reset, and account deactivation/deletion from the original user-management service are not yet exposed in the web UI.
- The original text data was intentionally not migrated. Confirm whether those files contain fixtures or important user data before designing an explicit data conversion.
